# Rules — SelfHeal

Rules established through the hackathon's official rules page and through decisions made in this chat. Split into business/competition rules (external, non-negotiable) and technical/coding/design/security rules (internal, project decisions).

---

## 1. Business / Competition Rules (external — from the hackathon organizer)

These come directly from the "Into the Scrape-Verse" rules page and govern eligibility. Violating any of these risks disqualification, not just a lower score.

1. Participation is online from anywhere, or in person in San Francisco on Aug 22.
2. Solo or team of up to 4; each participant may only be on one team.
3. **Required technology:** the project must use Bright Data Scraper Studio to create and run a custom web scraper.
4. The challenge is open-ended in category — application, automation, research platform, developer tool, data pipeline, AI product, or any other web-data-powered project is acceptable.
5. **Disqualifying condition:** using only an existing scraper from the Bright Data Scrapers Library does not qualify. The submission must include a custom scraper created using Scraper Studio.
6. **Disqualifying condition:** the project must use publicly available web data only. No private, login-protected, paywalled, personal, or restricted data.
7. **Timing rule:** the main coding and design work must begin after the hackathon starts. Discussing ideas, taking notes, planning architecture, or preparing diagrams beforehand is allowed.
8. Frameworks, open-source libraries, public APIs, templates, third-party tools, and publicly available assets may be used; only the original work completed during the hackathon is judged.
9. Every submission must include: a public source-code repository, a clear README, example structured output, a demo video showing the working project, and a clear explanation of how Bright Data Scraper Studio is used.
10. AI coding assistants are allowed, but their use must be disclosed.
11. Participants must understand the submitted code and be able to explain the scraper, project architecture, and technical decisions.
12. **Disqualifying risk:** projects entirely generated by AI without meaningful participant contribution, verification, or technical understanding may be rejected.
13. Prize structure: Suit-Up and Spider-Sense tracks award every team member; the Web-Slinger grand prize (NVIDIA DGX Spark or $5,000) goes to the winning team as a whole.
14. Registration alone enters participants into a raffle; building a project is not required for the raffle.
15. IP developed during the hackathon belongs to the participant/team that created it.
16–18. Standard conduct rules: treat all participants/organizers/judges with respect; harassment, discrimination, plagiarism, or judging manipulation causes disqualification; failure to follow rules or the Code of Conduct may result in disqualification.

## 2. Judging Criteria (external — six criteria, equally weighted)

1. Potential impact — does the project solve a clear, useful problem?
2. Creativity and innovation — is the approach to web-data collection original?
3. Technical excellence — is the implementation complete, reliable, well-structured?
4. Use of Scraper Studio — is it central to the project, not bolted on?
5. Reliability and self-healing — does the project account for site changes, missing data, or extraction failures?
6. Presentation — does the demo clearly explain the scraper workflow, structured output, and final product?

All project decisions in this document and elsewhere should be checked against these six criteria before being finalized.

## 3. Technical / Coding Rules (internal — decided in this chat)

- Do not fork or reuse an existing pre-built scraper repository as the project's core scraper — this violates rule 5 above and undermines judging criteria 2 and 3. Forking is acceptable only for infrastructure/plumbing: HTTP trigger/poll wrappers (e.g. Bright Data's official starter repos), dashboard UI scaffolding, schema-validation boilerplate, or hosting setup.
- The custom Scraper Studio collector itself, and the drift-detection/heal-orchestration logic (Layer 2), must be built by the team during the hackathon window — this is both a rule-7 compliance requirement and the actual differentiator being judged.
- Healing must remain **human-in-the-loop / approval-gated** — no auto-applying an AI-proposed fix without a review step. This is a deliberate design decision, not just a Bright Data default, because auditability is core to the product's value proposition.
- Every scrape result must pass through schema validation before being treated as "healthy" data — do not treat "the HTTP request succeeded" as equivalent to "the data is valid."
- Team must be able to explain every part of the codebase, especially Layer 2 — do not include AI-generated code that no team member can explain, per rule 11/12.
- Disclose any AI coding assistant usage in the README, per rule 10.

## 4. Security Rules

- Only scrape publicly available web data — no login-gated, paywalled, personal, or restricted content (rule 6, hard constraint).
- API tokens/credentials for Bright Data must not be committed to the public repository — use environment variables. (General best practice implied by public-repo requirement; specific secrets-management approach not yet decided — **TBD**.)
- No further security requirements were established in this chat — **TBD** for anything beyond the above (e.g. rate limiting, input sanitization on the dashboard, auth for the dashboard itself).

## 5. Design Rules

- Prioritize a deployed, polished, working product over a large unfinished feature set — a live URL judged in the "Best UI" track beats "clone and run npm install."
- The dashboard's core job is to make the self-healing loop **visible and provable**, not just to display data — every screen should trace back to demonstrating detection → heal → approval → resolution.
- Keep Layer 2 (validation/orchestration) simple and readable — a judge should be able to read the core loop in a couple of minutes; do not over-engineer this for hackathon scope.

## 6. Scope Rules

- MVP features only until the core detect → heal → approve loop works end-to-end (see `phases.md` for exact sequencing). Do not build stretch features (multi-tenant auth, alert integrations, multi-collector fleet views) before the MVP loop is proven.
- Positioning rule (from RCAFT research): do not pitch this as "nothing like this exists." Existing tools (ScrapeOps, Spidermon) already do detection/alerting — the honest, defensible claim is the narrower one: closing the loop from detection into an AI-proposed, human-approved repair specifically for Scraper Studio collectors.
